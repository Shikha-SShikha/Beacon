1
Query understanding before any search
The query is parsed for intent, entities, and constraints. "What inhibits STAT3 in colorectal cancer?" gets decomposed into: target entity (STAT3), relationship type (inhibition), disease context (colorectal cancer), and implicit task (find mechanisms or drugs). This shapes everything downstream.
entity extraction intent classification query expansion
2
Query rewriting / expansion often invisible to you
Your original query is rarely sent as-is. The system rewrites it into multiple variants — synonyms substituted, abbreviations expanded, related terms added. "STAT3 inhibitors colorectal" might become 3–5 parallel queries covering aliases and related concepts simultaneously.
synonym injection HyDE (hypothetical doc embedding) multi-query fan-out
3
Dual retrieval two parallel searches
Two retrieval methods run in parallel and their results are merged. Dense retrieval uses vector similarity (embedding your query and finding nearby document chunks). Sparse retrieval uses keyword matching (BM25 — classic search). Neither alone is sufficient; dense catches semantically related content, sparse catches exact terminology.
dense: vector similarity sparse: BM25 keyword hybrid merge
4
Reranking the critical filter
The initial retrieval returns ~50–200 candidate chunks. A separate, more expensive model then re-scores each one specifically for relevance to your query. This is where many failure modes from the taxonomy are introduced — negation, confidence, discourse role are all lost here because most rerankers score relevance, not epistemic quality.
cross-encoder reranker top-k selection (e.g. top 10) MMR diversity filter
5
Context assembly what the LLM actually sees
The top-ranked chunks are assembled into a prompt with your original query. The LLM never sees the full document corpus — only these retrieved fragments, typically 5–20 chunks totalling a few thousand words. The quality of everything before this step directly determines the quality of the answer.
chunk deduplication source metadata attached context window budget
6
Generation where your answer is written
The LLM reads the assembled context and generates an answer grounded in those chunks. It is instructed to cite sources and not hallucinate beyond what's provided. But if the retrieval steps surfaced the wrong chunks — or missed the right ones — the LLM has no way to know. It answers faithfully from bad inputs.
grounded generation citation attachment hallucination guardrails
7
Post-processing in more advanced tools
Sophisticated systems add a verification pass: fact-checking claims against retrieved sources, checking if the answer is actually supported by the cited chunk, flagging low-confidence statements, or triggering a second retrieval round if the answer looks incomplete. Most basic tools skip this entirely.
faithfulness check iterative retrieval confidence scoring
